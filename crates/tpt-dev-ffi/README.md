# tpt-dev-ffi

A framework for stateful C-style APIs. Each lifecycle state is a separate type, so an operation that is not allowed in the current state does not compile. Ownership of the library object is tied to the session, so it is released on every path.

- **Typestate sessions:** `Closed`, `Open` and `Streaming`. Each operation consumes the session and returns it in its new state.
- **Failures keep the session:** a failed operation returns the session unchanged, with the library's code. The caller decides what to do next.
- **Release on drop:** dropping a session frees the library object, whatever state it is in.
- **Checked handles:** `Handle<T>` is a non-null, typed pointer to a library object. It cannot be built from null.
- **Backend trait:** the library's operations are described once, in a `Backend` implementation. The session logic does not depend on the library.
- **Zero-copy views:** `Session::with_view` gives a closure a `View` of the library's bytes, with no copy. The view cannot be stored or returned, and no library call can run while it is alive.

## Ownership and borrow rules

1. The session owns the library object. It is destroyed exactly once, when the session is dropped, in whatever state it is in.
2. Transitions take the session by value. A handle cannot outlive the session that produced it: `with` and `with_view` borrow the session for the call.
3. Buffers passed to the library are borrowed for one call, through `with`. Nothing about them is kept after the call.
4. A `View` exists only inside the closure given to `with_view`. The closure takes the view for any lifetime (`for<'v>`), so the view cannot escape the call. The session is borrowed mutably for the whole call, so no library call runs while the view is alive. `tests/ui/view_*.rs` checks these rules at compile time.
5. `Backend::view` returns a slice tied to the backend borrow. The implementer must keep the bytes valid and unchanged for that borrow. This is the one `unsafe` contract the crate relies on, and it sits in the backend, not the session.

## Example

The `tests/c_library.rs` test defines a stateful library with `extern "C"` functions, wraps it in a `Backend`, and drives it through the typestates:

```rust,ignore
let mut backend = CBackend::default();
let session = Session::new(&mut backend).create().unwrap();
let streaming = session.open().unwrap().start().unwrap();
let open = streaming.stop().unwrap();
drop(open); // frees the library object
```

A `start` on a closed session does not compile. `tests/ui/start_closed.rs` checks that.

## Limits

- **Only the typestate is checked by the compiler.** The library's own rules are checked at run time, through the codes it returns.
- **One backend per session.** A session borrows its backend mutably, so two sessions cannot share one.
- **Views are read-only and scoped.** A `View` is valid only inside its closure, and it covers only the bytes that `Backend::view` exposes. Backends that expose no bytes use the default, which returns `None`.
- **Errors from `create` and `destroy`.** `create` reports its code, but `destroy` cannot fail, so cleanup errors are not reported.
- **C not compiled here.** The example library is Rust, exported through `extern "C"`, because the environment has no C compiler.
- **Automata and headers.** `tests/c_library.rs` checks two things. The `Closed`/`Open`/`Streaming` typestates match a `tpt_dev_automata::Machine` (deadlock-free, all states reachable, and every typestate transition is a machine transition). It also checks that the C header generated by `tpt_dev_headers` declares the library's exported functions. The machine is written by hand, not generated from the typestates, so the two can drift apart if one changes alone.
